# agent-runtime-project

# Phase 1
설계 결정 (Design Decisions용)

계산기에 eval 대신 AST 평가기를 쓴 이유: 모델이 만든 문자열을 그대로 실행하지 않으려고요.
모든 도구의 실패를 ToolExecutionError 하나로 통일한 이유: 에이전트 루프가 도구별 예외를 몰라도 되게요.
_fetch_* 내부 함수를 따로 둔 이유: 재시도 범위를 네트워크 호출 한 줄로 한정하려고요. 에러 변환까지 재시도되지 않게요.
서킷브레이커를 도구별로 둔 이유: API 하나가 죽어도 다른 도구는 계속 쓰게요.
MAX_TOOL_TURNS 상한과 for...else: 도구 호출이 무한 반복되는 걸 막는 장치예요.

실패 대응 (Failure Analysis용)

tenacity 재시도: RequestException에만, 3회, 지수 백오프(1~8초), reraise=True
서킷브레이커: 연속 3회 실패 시 300초 차단
잘못된 입력 처리: 없는 코인 ID(KeyError), 0으로 나누기 등을 명확한 메시지로 변환

실제로 겪은 버그 (이게 제일 좋은 재료예요)

모델의 응답을 contents에 무조건 추가하지 않았을 때, Gemini가 서로 다른 턴의 답을 뒤섞었던 문제예요. 원인과 수정이 구체적이라 "디버깅한 경험"으로 쓰기 좋아요.
도구 선언의 이름이 TOOL_REGISTRY 키와 달라서 호출이 실패한 문제도 있었어요.
앞서 말씀드렸듯 모델이 쉬운 계산(“1 더하기 1”)은 도구 없이 답하려 한 현상도 Phase 1에서 이미 나왔어요. Phase 2의 가짜 계산 문제와 이어지는 이야기예요.

# Phase 2
1. 프롬프트로 "계산기를 써라" 지시 → 도구 호출 없이 가짜 Expression/Result 출력
2. guardrail 추가 → 4번 연속 걸러져서 파이프라인 중단 (가짜 증거가 다음 단계로 안 넘어감)
3. 계산 Task 분리 → 1번 만에 통과

Phase 1의 서킷브레이커가 도구 쪽 실패를 다뤘다면, 이쪽은 에이전트의 거짓 보고를 다룬다는 대응 관계도 같이 쓰세요. 서킷브레이커가 Phase 2에는 이어지지 않는 점은 한계로 적고요. 재시도(tenacity)는 crew_tools.py가 같은 _fetch_* 함수를 쓰니까 그대로 유지돼요.
